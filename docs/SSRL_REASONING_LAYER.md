## 1. The existing graph design

### 1.1 The core principle: "say" versus "do"

Greenwashing is the **gap between what is said and what is done**. Two independent channels
feed **one** temporal knowledge graph:

```
┌───────────────────────────────────────────────────────────────┐
│  CHANNEL R — annual reports        →  the "SAY" side           │
│  source_type = "report"                                        │
│  → SustainabilityClaim, Goal, KPIObservation (reported)        │
├───────────────────────────────────────────────────────────────┤
│              ↓  the same Organization node  ↓                  │
├───────────────────────────────────────────────────────────────┤
│  CHANNEL N — third-party news      →  the "DO" side            │
│  source_type = "news"                                          │
│  → Controversy, Penalty, MediaReport, KPIObservation (observed)│
└───────────────────────────────────────────────────────────────┘
```

### 1.2 Three design properties

1. **Bitemporal** — nodes carry `valid_from` / `valid_to` / `is_current`; edges add
   `recorded_at`.
2. **Sentence-level traceability** — `source_pdf`, `page`, `sentence_index` survive every
   stage.
3. **No ground truth** — no labelled greenwashing dataset exists for Vietnam, so the system
   is not a classifier and emits no score: only **evidence plus an advisory opinion**.

## 2. The problem: four findings, all measured

> **Graph version:** every figure in §2 was measured on the build of 2026-07-04
> (10,573 nodes / 13,008 edges). After the Phase-0 repairs (P1/P2/P3-offline/P4, build
> 2026-07-15) it was 10,362 / 13,047. The current five-company snapshot is 6,918 / 9,797.
> Compare builds with `python src/run.py quality --label <name>`.

### 2.1 The graph is a star

Measured on the AAA graph (10,573 nodes / 13,008 edges / 40 relations):

| Metric | Value |
|---|---|
| Median degree | **1** |
| Leaf nodes (degree 1) | **8,798 / 10,573 = 83.2%** |
| Edge endpoints touching the AAA node | **36.8%** (AAA degree 9,564) |
| Claims reaching evidence **without** passing through AAA | **92 / 1,217 = 7.6%** |

So **97.5% of claims have exactly one path pattern** to evidence:

```
SustainabilityClaim ←claims— Organization(AAA) —mentionsOrganization/reportsKPI→ ConductNode
```

Every evidence candidate arrives by the **same two-step pattern**, so the path carries
**zero discriminative information** — and the agent degenerates into scoring the target
node's embedding, which is precisely the approach the paper argues is *worse* than
path-based reasoning.

The paper confirms the mechanism itself: SSRL's improvement scales with graph degree.

| Dataset | # facts | Median degree | SSRL improvement |
|---|---|---|---|
| FB15K-237 | 272,115 | **14** | best |
| NELL-995 | 154,213 | 1 | good (even relation distribution) |
| WN18RR | 86,835 | **2** | **worst** |
| **This graph (AAA)** | **13,008** | **1** | *(predicted ≈ 0)* |

### 2.2 Only 20.3% of edges were usable for training

This is the decisive metric, and it was the last one discovered.

In SSRL a training sample is **mask one edge `(e_s, r, e_q)` and make the agent find `e_q`
again**. The sample is only usable **if another path still exists after masking**. If `e_q`
is a degree-1 leaf, masking orphans it, BFS returns empty, and the sample is discarded.

Measured (masking both the forward and inverse edge, alternate path ≤ 3 hops):

| Group | Relation | % answerable |
|---|---|---|
| 💀 **Dead leaves** | `reportsKPI` *(37.6% of all edges!)* | **3.9%** |
| | `claims` *(the single most important relation)* | **1.0%** |
| | `setsGoal` | 0.8% |
| | `adoptsStandard` | 1.5% |
| | `subjectToRegulation` | 4.2% |
| ✅ **Walkable backbone** | `observedAtFacility` | **86.7%** |
| | `locatedIn` | 70.1% |
| | `ownsFacility` | 67.5% |
| | `isIn` | 64.5% |
| | `partnersWith` | **50.8%** |
| | `producedBy` | 42.8% |
| | `holdsCertification` | 30.6% |
| | **TOTAL** | **20.3%** (2,642 / 13,008) |

**This is really two graphs stacked on one plane:**

1. a **walkable structural skeleton** (`Facility` / `Location` / `Organization`, ownership,
   partnership) at 50–87%;
2. a **cloud of observation leaves** (`KPIObservation`, `SustainabilityClaim`, `Goal`)
   hanging off the issuer at **1–4%, effectively unwalkable**.

Group (2) is **47% of all edges**, and is exactly the two node classes a reasoning layer
**needs** to reach.

> For scale: FB60K in the paper also had only 21.3% label coverage at epoch 1 — but over
> 268K facts, i.e. ~57,000 usable samples. This graph had **2,642**. Twenty times fewer.

**Update (2026-08-06, five companies):** this metric is now reported directly by the
quality stage as **R1 = 47.2%**, with **R1′ (hub-free) = 26.7%**. The gap between the two
is the P5 hub dependency, quantified.

### 2.3 There is almost nothing to predict, and the "do" side is thin

| Target relation | Edges | | News-derived class | Count |
|---|---|---|---|---|
| `verifiedBy` | 39 | | `Controversy` | **2** |
| `contradictedBy` | **2** | | `Penalty` | **4** |
| `contradictedByMedia` | **0** | | `MediaReport` | 91 |

Two `Controversy` and four `Penalty` nodes for a listed company is far too little to reason
over. On the five-company snapshot it is still thin: 0 / 9 / 83 plus 298 news-side KPI
observations.

> **Principle:** a reasoning layer **cannot reason over evidence that does not exist.**

This is the same limit [SYSTEM_DESIGN.md](SYSTEM_DESIGN.md) §8.3 makes a first-class
caveat.

### 2.4 `identity_keys` was breaking the cross-company bridges

The graph was already a miniature multi-company graph: **438 `Organization` nodes** (the
issuer plus subsidiaries, partners, and companies named in the news). So do the *shared*
entities actually bridge two companies?

| Class | `identity_keys` (then) | Nodes | Degree 1 | **Links ≥ 2 Organizations** |
|---|---|---|---|---|
| `Person` | `["name"]` | 196 | 122 | **56** ✅ |
| `Location` | `["name","country"]` | 248 | 94 | **44** ✅ |
| `Product` | `["name"]` | 215 | 120 | 31 |
| `Facility` | `["name"]` | 277 | 99 | 29 |
| `Certification` | `["name","valid_from","validity_period"]` | 144 | 57 | 19 |
| **`Regulation`** | `["name","jurisdiction"]` | 264 | 252 | **5** ❌ |
| **`Standard`** | `["name","valid_from"]` | 331 | **310 (94%)** | **2** ❌ |

`Standard` and `Regulation` should have been the **strongest** bridges — every listed
Vietnamese company follows GRI and is subject to Circular 96/2020. In fact 310 of 331
`Standard` nodes were isolated leaves.

**Cause:** `valid_from` was in the identity key, so "GRI" in a 2021 report and "GRI" in a
2023 report were two different nodes. Multiply by 115 companies × 5 years and "ISO 14001"
shatters into hundreds of fragments.

> **This was a modelling error:** *an entity's identity is **what it is**, never **when we
> happened to observe it**.* Putting `valid_from` in `identity_keys` conflated identity with
> observation time.

And the schema already had the right mechanism for the time dimension:
`temporal_versions` + `supersedes`. Removing `valid_from` from the key **loses no temporal
information** — it moves that dimension to where the schema already put it. This is a fix
for **consistency with the project's own design**, not a schema tweak to make RL convenient.
That is the strongest way to defend it.

**Status: shipped.** This became principle P1 in
[TEMPORAL_KG_DESIGN.md](TEMPORAL_KG_DESIGN.md), is linted by the quality stage (Q2), and is
asserted in both directions by `test/test_schema_contract.py`. `Location` deliberately
keeps `country`: there are export operations and foreign subsidiaries, and dropping it
would merge same-named places across borders.

## 3. Validating by simulation: what is real and what is fake

Before changing anything, each proposed change was simulated **in memory**. This is the most
important section, because it **argues against this document's own proposal**.

### 3.1 Experiment 1 — fixing `identity_keys` alone is nearly useless (on one company)

Simulated merging `Standard` / `Certification` / `Regulation` / `Location` / `Authority` by
normalized name:

| | Before | After |
|---|---|---|
| Total trainable queries | 20.3% | **20.8%** |
| Median degree | 1 | **1** |

But per relation the prediction held exactly:

| Relation | Before | After | |
|---|---|---|---|
| `holdsCertification` | 30.6% | **44.7%** | +14 points |
| `subjectToRegulation` | 4.2% | **9.1%** | ×2.2 |
| `adoptsStandard` | 1.5% | **3.2%** | ×2.1 |
| `reportsKPI` | 3.9% | 3.9% | unchanged |

**Why did the total not move?**

1. **Dilution** — `reportsKPI` is 37.6% of all edges and sat still at 3.9%.
2. **On one company there is nothing to converge *to*** — only 260 duplicate nodes were
   found. Within AAA, "ISO 14001" appears a handful of times, giving degree 3. Across 115
   companies it would give degree ~115.

> ⇒ **Fixing `identity_keys` is necessary, but its benefit only materializes at
> multi-company scale.** The convergence effect multiplies with the number of companies.
> Measuring it on one company is measuring it under the one condition where it cannot work.

### 3.2 Experiment 2 — reifying keywords: most of the benefit is fake

Simulated letting `SustainabilityClaim`, `KPIObservation`, `MediaReport` and `Goal` point
into a shared `ClaimKeyword` pool, sweeping the keyword node's **degree cap** (`df_max`):

| Keyword degree cap | Keyword edges | Max hub degree | `claims` | `reportsKPI` | **TOTAL** | **Median degree** | **claim→conduct (hub-free)** |
|---|---|---|---|---|---|---|---|
| **≤ 20** *(honest)* | 8,330 | 20 | 71.6% | 17.6% | **36.5%** | **1** | **16.0%** |
| ≤ 50 | 15,067 | 50 | 85.7% | 38.6% | 47.1% | 2 | 27.3% |
| **≤ 400** *(reckless)* | 35,905 | **346** | 97.9% | 90.0% | **68.4%** | **4** | **71.8%** |

**Every attractive number rises monotonically with hub size.** The impressive
"68.4% / degree 4 / 71.8%" result exists **only** if one keyword is allowed to connect 346
nodes.

> ⚠️ Plainly: that does **not** make the graph denser — it **replaces** one hub (the issuer,
> degree 9,564) with a few dozen keyword hubs of degree ~346. A star becomes a bushier star.

### 3.3 The "empty calories" trap

The new path a keyword creates looks like this:

```
Claim C  —hasKeyword→  "moi_truong"  —hasKeyword⁻¹→  KPI K
```

What does it say? It says: *"C and K both contain the phrase 'môi trường'."*

That is **exactly** the token-overlap signal `claims_vs_conduct` already computes. Reifying
it just re-encodes that signal as graph structure. An RL agent trained on it would learn to
**reproduce token overlap, by a route a thousand times more expensive**.

> **Empty calories = topology metrics improve, reasoning capability does not.**
> Four weeks and a GPU to rebuild what twenty lines of Python already do.

**Genuinely new information comes only from the structural skeleton:**

```
C1 —claims⁻¹→ O_AAA —partnersWith→ O_SUP —subjectToPenalty→ P1
                     └────────── no shared keyword at all ──────────┘
```

The claim *"green supply chain"* and the penalty *"effluent above permitted limits"* share
no token. Only the **supply-chain structure** connects them. **That** is what the LLM
adjudicator cannot do. **That** is the contribution.

And those relations (`partnersWith` 50.8%, `ownsFacility` 67.5%, `observedAtFacility` 86.7%)
only become rich with **many companies**.

### 3.4 Three conclusions, each backed by numbers

1. **Keyword reification is worthwhile but must be degree-capped** (proposed `df ≤ 20`).
   `claims` going from **1.0% → 71.6%** is a **real** improvement on the single most
   important relation. Removing the cap is self-deception.
2. **One company is never enough.** With the honest setting (`df ≤ 20`) the gate still
   failed: median degree **1**, claim→conduct only **16.0%**. This is a **measured**
   conclusion, not a guess. Multi-company is **necessary, not optional**.
3. **The gate metric had to change** (§6.1) — "total % answerable" can be inflated with
   junk hubs.

### 4.2 Reify `ClaimKeyword`, with a degree cap — **not done**

`ClaimKeyword` exists (141 nodes, 163 `hasKeyword` edges) — **but only claims have keywords;

**Proposal:** allow `hasKeyword` from `MediaReport` / `Controversy` / `KPIObservation` →

**Mandatory: the `df ≤ 20` degree cap** (§3.2). Keyword edges must also carry a distinct
type tag, so evaluation can separate "pure keyword paths" from "structural paths".

How to present it:

> *"I am not adding edges to please an RL agent. I am **moving a retrieval signal that is
> already in use** out of code and into the graph, where it is **auditable and queryable in
> Cypher**. And I measured which part of the benefit is real and which part is a
> super-hub artifact."*

### 4.3 Multi-company — **done, 5 tickers**

Companies from the **same sector** (construction / building materials) were the right
choice: they have the highest chance of sharing suppliers, locations and regulators. The
registry now covers AAA, ACC, ACG, ADP, AGG.

### 4.4 Fill the "do"-side gap — **still open**

Re-extract articles containing `Controversy` / `Penalty`. **This must happen whether or not
SSRL is built** — see §2.3.

### 4.5 Do not over-merge

Naively merging `Standard` / `Regulation` into global nodes creates a **super-hub** ("GRI",
degree ~115). The agent learns to route through them and produces:

> AAA adopts GRI ← GRI ← BBB adopts GRI, and BBB was penalized ⟹ ???

**A path, but not evidence.** This is Freebase's classic hub problem.

| ✅ Good bridges (keep in the action space) | ❌ Junk bridges (exclude or down-weight) |
|---|---|
| Shared supplier / partner / parent | "both follow GRI" |
| Shared `Facility` / `Location` (same industrial park) | "both are subject to Circular 96" |
| Shared `Authority` (the regulator that fined A also certified B) | The `Country` node "Việt Nam" |
| Shared `Person` (interlocking directorates) | Over-common keywords (`df > 20`) |

⇒ Merge `Standard` / `Regulation` **for data correctness**, but **exclude them from the
action space**. The quality stage already implements the measurement half of this via
`REFERENCE_CLASSES`.

### 4.6 Two anchors per T2 node (P3) — **partly shipped**

The cheapest Phase-0 item by impact. Event nodes were unreachable
(`KPIObservation` 4.1% at degree ≥ 2) while `Investment` — designed with two anchors —
reached 50.4% in the same pipeline. Fixed at the `extract_triples` prompt for new
extractions and patched offline by `anchor_kpi`'s gazetteer for already-paid data. Measured
by Q7(e), now 28.3% overall and 26.5% for `KPIObservation`.

Still blocked: anchoring news events (`Controversy`, `Penalty`, `MediaReport`) to a
`Facility` needs three additional schema pairs — [ROADMAP.md](ROADMAP.md) §2.3.

### 4.7 A degree policy for the issuer node itself (P5) — **partly shipped**

The keyword cap (§3.2) only addresses half the hub problem. **The largest hub is the issuer
node.** Nearly every useful path steps through it at the first hop, and MINERVA/MultiHopKG
truncate or sample the action space to ~200–400 actions — so uniform sampling over thousands
of neighbours kills the agent at hop 1.

Two responses:

- **Trainer-side (unbuilt):** factored action selection — pick the **relation** first
  (~48 labels), then the target within that group.
- **Export-side (built):** `export_kgc` decomposes hub clusters into synthetic `HubBucket`
  nodes for the export view only, taking AAA from degree 9,511 to 542. See
  [EXPORT_KGC.md](EXPORT_KGC.md).

## 5. Applying SSRL to a problem with no labels

### 5.1 SSRL needs no human labels

"Self-supervised" means the training signal is generated from the graph structure itself:

1. take an edge that **already exists**: `(e_s, r, e_q)`;
2. **mask it** (both the forward and the inverse edge);
3. query the agent: *"from `e_s`, following `r`, find the target"*;
4. the agent walks the graph; reaching `e_q` is rewarded;
5. **supervision labels** are generated by **BFS**: enumerate *every* correct path, mark
   every edge on a correct path as `1` and the rest `0`.

**No human labels anywhere.** Ground truth is **the edges that already exist**, extracted by
the pipeline from reports and news.

> ✅ **The "no greenwashing labels" constraint is orthogonal to this method.** It kills a
> supervised classifier; it does not obstruct SSRL. This is the strongest reason for
> choosing this particular paper.

### 5.2 A required technicality: inverse edges

The schema is directed, and evidence nodes usually point **into** `Organization`:

```
MediaReport —mentionsOrganization→ Organization      (points IN)
Organization —subjectToPenalty→ Penalty              (points OUT)
```

An agent standing on `Organization` cannot walk back to `MediaReport`. MINERVA/MultiHopKG
always add **inverse edges** (standard, free preprocessing): 48 relations become 96. The
agent can walk both ways while still **knowing** which way it is walking.

Per P6, these belong to the **export tier only** — never written to Neo4j or to
`resolved_graph.json`, with an `_inv` naming convention and an `is_inverse` flag.

### 5.3 A worked BFS labelling example

> ⚠️ **P8 constraint:** BFS labelling **must run on each query's temporal subgraph** — only
> edges with `valid_from ≤ t_query` (and, on the knowledge-time axis,
> `recorded_at ≤ t_query`). Running BFS on the unmasked whole graph would label edges `1`
> that the agent is forbidden to walk at RL/inference time (e.g. a route through 2024
> evidence for a query anchored in 2021), producing an SL↔RL distribution mismatch — exactly
> the failure mode that makes the supervised phase counterproductive.

**Nodes:**

| Symbol | Class | Content |
|---|---|---|
| `O_AAA` | `Organization` | CTCP Nhựa An Phát Xanh |
| `F1` | `Facility` | Hải Dương plant |
| `F2` | `Facility` | Yên Bái plant |
| `I1` | `Initiative` | Emission-reduction initiative |
| `GRI` | `Standard` | GRI Standards |
| `ISO14001` / `ISO9001` | `Certification` | |
| `L1` | `Location` | Hải Dương |

**Edges (all legal in `schema.json`):**

```
O_AAA  —ownsFacility→        F1
O_AAA  —ownsFacility→        F2
O_AAA  —takesPartIn→         I1
O_AAA  —adoptsStandard→      GRI
F1     —holdsCertification→  ISO14001
F1     —locatedIn→           L1
F2     —holdsCertification→  ISO9001
I1     —aimsForCertification→ ISO14001

O_AAA  —holdsCertification→  ISO14001    ← ❌ MASKED
O_AAA  —holdsCertification→  ISO9001     ← ❌ MASKED
```

**Query:** `q = (e_s = O_AAA, r = holdsCertification, ?)` with
`E_all = { ISO14001, ISO9001 }` — two correct answers, a "to-many" query.

> **The "target" is not a fixed node type.** The target is the *object of the edge that was
> just masked*. Each query defines its own target.

**BFS, four steps.**

1. Remove self-loops from every node **except** those in `E_all`.
2. BFS from `O_AAA` finds **three correct paths**:

```
① O_AAA —ownsFacility→ F1 —holdsCertification→  ISO14001   ✓
② O_AAA —takesPartIn→  I1 —aimsForCertification→ ISO14001  ✓
③ O_AAA —ownsFacility→ F2 —holdsCertification→  ISO9001    ✓
```

3. Collect nodes on correct paths: `C = {F1, I1, F2}`.
4. Emit labels.

> ⚠️ **The label `y_t` is a vector over node `t`'s ACTION SPACE — its outgoing edges.**
> **Labels live on EDGES, not on NODES.** This is the easiest thing to get wrong.

Labels at `O_AAA`:

| # | Action (**edge**) | Leads to | Label | Why |
|---|---|---|---|---|
| 0 | *self-loop* | `O_AAA` | **0** | not at the target; standing still is not allowed |
| 1 | `ownsFacility` | `F1` | **1** | on correct path ① |
| 2 | `ownsFacility` | `F2` | **1** | on correct path ③ |
| 3 | `takesPartIn` | `I1` | **1** | on correct path ② |
| 4 | `adoptsStandard` | `GRI` | **0** | dead end |

⇒ `y_O_AAA = [0, 1, 1, 1, 0]`, `y_F1 = [0, 1, 0]`, and at the target `ISO14001` the
self-loop is **1** — *"you have arrived, stay here."*

**Why SSRL beats plain RL.** Plain RL is rewarded for finding *one* path, so it keeps taking
path ① and never explores ②. SSRL marks **every** edge on **every** correct path, so the
agent learns the whole correct region. That is the "information density" the paper describes.

**The survival condition.** Masking only produces a usable sample **if another path remains
afterwards**. If `ISO14001` were a degree-1 leaf, masking orphans it and the sample is
discarded — which was the case for 79.7% of edges (§2.2).

### 5.4 At inference: what is actually wanted

```
q = (e_s = C1, r = contradictedBy, ?)
```

The agent finds:

```
C1 —claims⁻¹→ O_AAA —partnersWith→ O_SUP —subjectToPenalty→ P1
```

**Target = `P1`.** And **the path is the explanation** that goes into the dossier:

> *"AAA claims a green supply chain → but its packaging partner X was penalized for effluent
> violations in 2024."*

The current LLM adjudicator can **never** find this: it compares a claim's text against one
article's text, with no way to traverse `O_SUP`. **This is the contribution.**

### 5.5 Handling a scarce target relation

`contradictedBy` has only 2 edges (§2.3), so the agent can barely learn an embedding for it.

| Approach | Assessment |
|---|---|
| ① Multiply edges via multi-company | Necessary, not sufficient |
| ② **Train on the dense relations so they compose into evidence paths** — `partnersWith`, `ownsFacility`, `subjectToPenalty`, `observedAtFacility` (exactly the 50–87% group) | ⭐ **Recommended** — avoids the scarcity problem entirely |
| ③ Use the LLM's adjudications as labels | ❌ **Forbidden** — see §5.6 |

With ②, `contradictedBy` never needs to be dense: the agent learns *how to walk a supply
chain*, then a query like `(O_AAA, subjectToPenalty, ?)` is expanded 3–4 hops. **The LLM
remains the judge** — the agent *proposes* `P1` with its path, the LLM *adjudicates* whether
`P1` genuinely contradicts `C1`.

### 5.6 The circularity trap

> **Never** train the agent on the LLM's adjudications and then **evaluate against those
> same adjudications.**

That is distilling the adjudicating model and then measuring how closely you resemble it —
**unfalsifiable**, and it will be dismissed on sight.

**Correct:** train on **held-out extracted structural edges** (§5.1).

### 5.7 Where it sits in the system — the output does not change

```
build_resolved → resolved_graph.json
   ├─► [PARTLY BUILT] export_kgc (11)     hub decomposition for the export view
   ├─► [NOT BUILT]    dataset export      graph → (e_s, r, e_q) triples + BFS labels
   ├─► [NOT BUILT]    trainer             SL warm-up → RL (base: MultiHopKG / PyTorch)
   └─► [NOT BUILT]    path evidence       per claim: walk → candidates + PATHS
                                                   │
claims_vs_conduct (07) ◄───────────────────────────┘
   retrieval    = token overlap ∪ indicator tier ∪ path walker   ← the agent PROPOSES
   adjudication = LLM (unchanged)                                ← the LLM still JUDGES
   dossier + "reasoning_path": [...]                             ← existing fields byte-identical
```

**The agent is a retriever and an explainer, never a judge.** The "advisory, not a score"
framing is preserved exactly.

Per P7, `reasoning_path` must serialize the **list of edges with per-edge provenance**, not
just a list of nodes — the sellable property of path evidence is that a reader can check
each step back to the sentence that produced it.

### 5.8 Evaluating without labels

| Tier | Metric | Why it is valid |
|---|---|---|
| **Primary** | Link prediction on held-out structural edges: **Hits@1/@3/@10, MRR** | The paper's own protocol. **Needs no ground truth.** Ablation = SSRL vs plain RL |
| **Secondary** ⭐ | **Structural-path retrieval recall**: does the agent find evidence that token overlap **missed**? | Only genuinely new candidates go to the LLM. **This is the most important result** — it is what proves the work is not empty calories (§3.3) |
| **Supplementary** | The 30 hand-annotated cases in `config/evaluation/ablation_cases.json` | Already on disk |

## 6. Execution plan

### 6.1 The gate

The old metric ("total % of answerable queries") was **rejected** — it can be inflated with
junk hubs (§3.2). The correct gate:

> **The share of claims that reach a conduct node via a path containing AT LEAST ONE
> STRUCTURAL EDGE** (`partnersWith`, `ownsFacility`, `observedAtFacility`, `worksAt`,
> `locatedIn`, `producedBy`, …) — **pure keyword paths do not count.**

Only structural paths carry information the cross-check's token overlap does not already
have.

This is Q7(d) in the quality report, and it now has an answer:

| Graph | Companies | Q7(d) claim→conduct structural |
|---|---|---|
| Simulated, `df ≤ 20` | 1 | **16.0%** |
| Measured `with_news_5co_20260806` | 5 | **44.6%** |

**The gate's own question — "does this rise materially from 1 to 3 companies?" — is answered
yes.** Two caveats before treating it as passed:

- the two figures come from different graph builds and different keyword settings, so this
  is a strong indication rather than a controlled experiment;
- the companion conditions have not all been met: Q2 is 6 violations, not 0, and Q7(e) is
  28.3%, below the 30% target.

The honest reading: the multi-company hypothesis of §3.4 is **supported**, and a controlled
re-measurement across 1 / 3 / 5 companies on one build would settle it.

### 6.2 Sequence

```
①  identity_keys + keyword reify (df ≤ 20)     [free, minutes]      ← ① DONE, keyword part NOT
       → entities --no-llm → neo4j_load
       ⚠ do NOT expect the gate to pass — simulated: still fails on one company

②  Unblock the LLM providers                    [DONE]
       gemini / deepseek / openai are all available now

③  Pilot 3+ companies in the SAME sector → full pipeline   [DONE — 5 tickers]

④  🚦 GATE: measure "% of claims with a STRUCTURAL path to conduct"
       1 co = 16.0%  →  5 co = 44.6%  →  extrapolate → decide whether to scale to 115
```

> **A negative result is also a good thesis chapter.** Had the metric not moved from 1 to 3
> companies, that would have proved — **with numbers** — that *single-company Graph-RAG lacks
> the density for path-based reasoning*. That is a defensible finding, and all of Phase 0's
> value survives either way.

### 6.3 Cost matrix

**The good news:** `all_validated_triples.json` stores full `properties`, and the resolver
**recomputes** identity signatures from the schema rather than trusting the extractor's
`stable_id`. So **LLM extraction results are frozen into a reusable asset.**

| Phase-0 item | Must re-run | LLM? | Embedding? | Cost |
|---|---|---|---|---|
| `identity_keys` fix | `entities --no-llm` → `neo4j_load` | ❌ | ❌ | **free**, minutes |
| Keyword reify | a new offline script → `neo4j_load` | ❌ | ❌ | **free** |
| Conduct-side patching | `extract_triples --doc <news>` → 03 → 05 → 06 | ✅ small | ❌ | tens of calls |
| Multi-company | `extract` + `extract_triples` **from scratch** per company | ✅ **large** | ❌ | **~95% of total cost** |
| Dossier refresh after a graph change | 07 → 08 → 09 | ✅ | ❌ | ~$0.5, ~13 minutes |

Keyword reification costs no LLM because the signal the cross-check uses is **deterministic
token overlap**. If it needed an LLM it would not have been an *already available* signal.

**Scale of the multi-company step:** AAA alone is 43 documents / 1,370 pages, and both
extraction stages call the LLM **per page**. 3–8 companies is ~4,000–11,000 pages, i.e.
~8,000–22,000 LLM calls.

**Where embeddings come back:**

1. **`entities` Stage B.2** (`gemini-embedding-001`) — currently off. At multi-company scale
   entity resolution gets much harder, so this is where embeddings genuinely earn their
   cost. A local CPU sentence-encoder is the free alternative — [ROADMAP.md](ROADMAP.md) §2.5.
2. **`claims_vs_conduct --embed`** — optional, off.
3. **SSRL itself needs no embedding API.** MINERVA/MultiHopKG learn entity and relation
   embeddings from scratch by backpropagation. The reasoning layer is **API-free** — it
   costs GPU time only.

### 6.4 Phases

| Phase | Time | Deliverable | Risk |
|---|---|---|---|
| **0. identity_keys + keyword + multi-company pilot + conduct patching** | ~1–2 weeks | Better cross-check; topical links queryable in Cypher. **A thesis chapter even if SSRL is dropped** | Low |
| **🚦 GATE** (§6.1) | — | Continue or stop | — |
| 1. KGC dataset export + plain-RL baseline | 1–1.5 weeks | Hits@k / MRR baseline | Medium |
| 2. SSRL: BFS priming labels + SL→RL | ~1 week | Reproduce the paper on an ESG KG | Medium |
| 3. Integrate into the cross-check | 0.5–1 week | `reasoning_path`; **existing output unchanged** | Low |
| 4. Evaluation (§5.8) | 0.5–1 week | Ablation + recall study | Low |

**Total: ~4–6 weeks.** Phase 0 is now largely done.

### 6.5 Training time

Compute is **not** the bottleneck. The paper's "18–72 hours on a V100" is for graphs of
100–270K facts.

| Scale | Per run |
|---|---|
| AAA today (~13K edges) | ~1–3 GPU-hours *(but meaningless — it is a star)* |
| Multi-company, ~15–20 firms | ~4–10 GPU-hours ← **the realistic target** |
| All 115 firms (~100–500K edges) | ~8–20 GPU-hours on a modern card |

**But 5–8 runs are needed.** The paper shows the SL phase's epoch count is a **critical,
dataset-dependent hyperparameter** — optimal at 3 / 2 / 5 / 7 epochs across four datasets,
with **no universal value**, and **too much SL training degrades performance**. Budget 1–2
weeks of background GPU time.

### 6.6 Difficulty: 8/10

Not because of the ML — the method is well specified and reference code exists — but because
of:

1. **Research-code archaeology.** The original MINERVA is TensorFlow 1.x; use the
   **MultiHopKG (PyTorch) base** instead.
2. **Mandatory graph restructuring first** — the real barrier (§3).
3. **Hyperparameter sensitivity** (§6.5).
4. **A real risk that the improvement is small.** On a star-shaped graph that is the *most
   likely* outcome.

## 7. Two extensions beyond the original paper

### 7.1 Relation-balanced priming labels

The graph is heavily skewed: `reportsKPI` is **37.6%** of all edges. The paper shows skewed
relation distributions **reduce** SSRL's effectiveness (WN18RR, FB60K) and states plainly in
its conclusion that generating labels according to the relation distribution is **future work
they did not do**.

`config/degenerate_relations.json` already encodes the first step of this: `reportsKPI` is
excluded from `R1_trainable`, because a KPI observation listed under its own issuer is an
enumeration edge, not an inference a walker should be scored on predicting.

### 7.2 Time-respecting reasoning

The paper's KG is **static**; this graph is **bitemporal**. The agent must not walk from a
2021 claim to 2024 evidence when reasoning about what was knowable in 2021.

⚠️ **Position the novelty correctly.** Temporal action-space constraints on temporal KGs are
**not new** — TITer / TimeTraveler (Sun et al., EMNLP 2021, arXiv:2109.04101) did this in
2021 (action = (relation, entity, timestamp), relative-time encoding, time-shaped reward)
and **must be cited**. The genuine contribution is three-part (see
[TEMPORAL_KG_DESIGN.md](TEMPORAL_KG_DESIGN.md) P8):

1. **SSRL's dense BFS labels in a temporal setting** — the original SSRL paper works on
   static KGs only, and the temporal mask must be applied **identically in all three
   places**: BFS label generation, the RL action space, and the inference action space.
2. **A two-axis bitemporal mask** — TITer has event time only; this graph adds
   `recorded_at`. For greenwashing the knowledge-time axis is the causally correct one: a
   2021 report cannot be accused of contradicting information that first appeared in 2024.
3. **Relation-balanced labels** (§7.1) — the original paper's own stated future work.

## 8. The defence in six points

1. **The problem is real and measured**, not conjectured: 83.2% leaves, median degree 1,
   **97.5% of claims with a single path pattern**, and **only 20.3% of edges usable for
   training**.
2. **The schema change fixes a modelling error** and is consistent with the project's own
   bitemporal design — *identity ≠ observation time* — not an arbitrary edit to serve RL.
3. **The proposal was argued against with simulation** (§3): most of the keyword benefit
   turned out to be **fake**, caused by super-hubs — which changed both the design and the
   gate metric.
4. **SSRL fits a label-free problem**: supervision is generated by BFS over existing edges,
   so the "no ground truth" constraint is **orthogonal** to the method.
5. **The contribution is a new capability**: indirect multi-hop supply-chain evidence that
   the LLM adjudicator **structurally cannot** find — plus two extensions (§7) the original
   paper did not attempt.
6. **There is a quantitative gate, and a negative result is still a defensible finding.**
